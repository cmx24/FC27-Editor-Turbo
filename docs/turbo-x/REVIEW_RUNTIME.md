## Findings (ordered by severity)

### 1. D — CMTracker "Create from his career data..." now lands on a page that can never open the dialog (confirmed)
- ui/ui_cmtracker.cpp:285-286: `request_create_from(app, in_db); app.request_tab = 0;` → area_for(0) = Players/PlayerEdit.
- The pending create (`g_pending_create`, ui/ui_presets.cpp:727-731) is consumed only inside `player_preset_buttons` (ui/ui_presets.cpp:956-959), whose sole remaining caller is the Create & clone page (ui/ui_player_creation.cpp:284). The two callers that drew it on the player page were deleted by tx-menus (classic "Everything" tab → draw_players, and draw_player_page).
- Consequence: silent no-op on click (popup closes, PlayerEdit opens with the player selected, no Create dialog). Worse: `g_pending_create` stays armed, so the next time the owner opens Create & clone with that player still selected the "##pcreate" modal pops open by itself.
- Fix: replace `app.request_tab = 0;` with `app.go(shell::Page::CreatePlayer);`.

### 2. F — slider release path can cost a full process-memory scan + 772 KB file read per release (confirmed by reading the path)
- ui/ui_game_settings.cpp:440-445: write is once per release (`IsItemActive` → stash in `g.edit`; `IsItemDeactivatedAfterEdit` → `apply_one`). Not every frame. Correct, including Ctrl+click typing (value tracked while active, written on Enter/defocus).
- apply_one → live_write: when `g.live_addr` is 0 or the cached bytes no longer match (ui/ui_game_settings.cpp:208-228), it calls `read_file_now` (full Settings file parse) and `live::find_block` over every region from `app.regions_hook()` on the overlay thread, mid-frame, inside the open ImGui table. Same path as the old Load button, but now triggered by each slider release; while the block cannot be found (e.g. at Press Any Key, or after the game rewrote the block itself) every release repeats the whole scan. Frame hitch, not a crash. Also: on failure the slider snaps back to `cur` next frame and `live_line` says why — acceptable.
- Smallest mitigation: remember a failed find for N seconds (or until the file mtime changes) and refuse further releases with the same `msg` without rescanning.

### 3. F — journal is overwritten per slider; the comment promises an Undo that does not exist (confirmed)
- ui/ui_game_settings.cpp:238 writes `settings_live_journal.json` with only the entries of *this* write (`r.changed` = one slider). Each release replaces the previous file, so after dragging three sliders only the last one's old byte is recorded. Nothing reads the journal anywhere (grep: only the writer and `journal_json`). The header comment at :187 ("the journal the Undo path reads") is false. Not a runtime hazard; a false safety claim.
- Related stale UI: ui/ui_changes.cpp:701 still lists "Game slider presets / Discard staged → GameplayPresets", but that page no longer stages anything (the Discard button only appears when the *tactics* page staged a file).

### 4. F — `live_line` can be shown stale (plausible, low)
- `g.live_line` (ui/ui_game_settings.cpp:462-466) is never cleared: not on Refresh, not when `read_file_now` finds the game saved new values, not when the owner leaves and returns. "X = 60 written (not proven in game)" stays on screen after the game itself reset the value. Fix: clear it in `read_file_now` (Refresh) or when `current_value` of that id no longer equals the written value.

### 5. F — stale-address write (pre-existing path, now reachable more often; plausible)
- ui/ui_game_settings.cpp:208-211: if the old block address still reads back exactly `g.live_bytes` (freed-but-not-overwritten memory after the game reallocates the Custom block, e.g. a career reload), Turbo writes to the dead address, read-back agrees, and reports "written". Same logic as the previous Load; sliders make it a per-release event. Cheap hardening: also require the newest Settings file's Custom bytes to equal `g.live_bytes` at the time of reuse, or revalidate `writable_hook(addr, n)` (write_block already does the latter, so only the "freed but still mapped" case remains).

### 6. G — picker UX regressions, no crash (confirmed)
- Choice mode (ui/ui_visual_picker.cpp:909-916 `subset_source`, 1049-1052 `blank_tile`): band hair/beard ids that the game ships no picture for are `kSrcBlank` and therefore hidden behind "Show N without picture" by default. The 3D chooser can open nearly empty for a real-face player if most band ids are model-only. Not a crash; the toggle restores them.
- Tattoo picker opens with group "Made for this area" preselected (:917-920); `filter()` :1071 has no "always show the current value" exception for the group filter (only :1073 scope has it), so a current tattoo that the save's table marks for other areas is not in the grid until the combo is changed. Apply stays disabled until a change, so nothing wrong is written.

### 7. D — pre-existing, not introduced by the merge (noting for completeness)
- ui/ui_home.cpp:110-113 "Manager miniface (3D)" sets `manager_edit_tab() = 2` but navigates to LooksStudio; `manager_edit_tab()` is only consumed by the Staff page's `##mtabs` (ui/ui_teams.cpp:829), which has tabs 0/1 (+ Miniface). The 3D request itself is consumed in ui/ui_images.cpp:1330 whenever the manager miniface tab bar draws. Same behaviour as the non-tree40 branch before the merge.
